# Security and Provider Policy

## Purpose

Cliostra is intended to orchestrate AI agents that are already installed and authenticated on a user's machine. That creates two separate questions for every integration:

1. **Can the agent be automated technically?**
2. **Is that automation compatible with the provider's current terms and safety model?**

Cliostra must treat those as separate checks.

A provider can expose a technically usable CLI while still placing contractual restrictions on how third-party software may invoke it. A detected agent must therefore not be considered enabled simply because Cliostra can launch its executable.

## Project posture

The project should prefer the most conservative interpretation when provider policy is unclear.

A stable integration should use documented local or programmatic interfaces and preserve the provider's own controls rather than disabling them.

Cliostra should not intentionally:

- copy, export, or reuse access tokens, cookies, refresh tokens, or browser sessions;
- reverse engineer private protocols to simulate a provider client;
- automate web applications when a supported programmatic interface is required;
- bypass quotas, credits, rate limits, approvals, sandboxes, or safety controls;
- rotate accounts to evade provider limits;
- turn a personal subscription into an unauthorised shared service;
- hide the origin of automated requests;
- present an ambiguous provider integration as fully supported.

## Detection is not authorization

Cliostra should model provider readiness as a progression rather than a boolean.

An agent may be:

- detected;
- installed;
- executable;
- programmatically usable;
- capability-probed;
- policy-reviewed;
- enabled as a worker;
- enabled as a host.

This distinction is important for the TUI. Users should be able to see that an application exists without Cliostra implying that it can or should automate it.

## Credentials

Cliostra is not a credential manager for AI providers.

Authentication should remain the responsibility of each official agent or provider client. Cliostra may launch an already authenticated tool, but it should not need to inspect the secret material that makes the authentication work.

The runtime should avoid logging or returning:

- API keys;
- access tokens;
- refresh tokens;
- cookies;
- keyring contents;
- credential files;
- sensitive environment variables.

If a provider exposes a documented opaque session identifier that is safe to persist, Cliostra may evaluate storing that identifier for session continuation. Session identifiers must not be assumed safe until their semantics are understood.

## Process execution

Worker execution is a high-trust boundary.

The implementation should favor structured process invocation rather than shell interpolation. Model-generated text must not be concatenated into arbitrary shell commands used to launch workers.

The design should account for:

- explicit executable selection;
- explicit argument construction;
- controlled working directories;
- path normalization;
- cancellation;
- timeout policy;
- process-tree cleanup;
- stdout/stderr separation;
- output size limits;
- environment-variable filtering;
- platform-specific process behavior.

The exact implementation is not fixed yet, but the security properties are requirements.

## Permissions

Delegating a task must not automatically imply unrestricted machine access.

When a worker supports permission controls, Cliostra should preserve them and allow the host/user to scope access such as:

- read-only filesystem access;
- write access to a selected workspace;
- shell execution;
- network access;
- external MCP tools;
- provider-native tools;
- secrets or environment access.

Background execution must not become a reason to silently disable approvals or sandboxes.

If a task requires a permission that cannot be safely granted non-interactively, the job should be able to stop, wait for intervention, or fail clearly rather than bypass the control.

## Context and result handling

A worker's output is untrusted content from the perspective of Cliostra's authorization layer.

Worker output must not be able to grant itself new permissions by saying things such as:

- enable full filesystem access;
- connect another provider;
- reveal a secret;
- disable the sandbox;
- increase orchestration depth;
- modify the policy configuration.

Authorization decisions belong to local configuration, the host's allowed inputs, and explicit user choices — not to text generated by a worker.

Operational output and final result output should be separated. The host should receive the final useful result by default, while diagnostic logs stay outside the model context unless explicitly requested.

## Prompt injection

Cliostra sits between agents that may consume untrusted repository content, web content, documentation, tool outputs, and messages. Indirect prompt injection is therefore part of the threat model.

Security-sensitive decisions must not depend solely on a model correctly ignoring malicious instructions.

The runtime should enforce boundaries structurally where possible:

- permissions outside the prompt;
- workspace restrictions outside the prompt;
- provider allow/deny state outside the prompt;
- credentials inaccessible to normal task content;
- tool/capability metadata validated by Cliostra;
- worker results treated as data, not policy instructions.

Relevant research includes AgentDojo and ongoing Model Context Protocol security work on tool poisoning, capability trust, and adversarial tool ecosystems.

## Skills and external tools

Skills, MCP servers, hooks, plugins, and other reusable capabilities can expand a worker's effective permissions.

Cliostra should not automatically assign every discovered skill or tool to every worker.

Before enabling an additional capability, the design should account for:

- source trust;
- filesystem access;
- network access;
- secret access;
- commands it can execute;
- context cost;
- compatibility with the worker;
- prompt-injection exposure.

Skill assignment should be explicit or governed by a visible local policy.

## Provider review

Every provider adapter should have a small policy record that can be updated independently from the core runtime.

Before marking an adapter stable, the project should verify:

- an official programmatic or automation surface exists;
- the surface can be used without extracting private credentials;
- the intended third-party orchestration pattern is permitted or sufficiently documented;
- quota and rate-limit behavior is respected;
- the provider's sandbox/approval model can remain active;
- session continuation behavior is understood;
- cancellation and failure behavior are manageable;
- provider terms do not prohibit the intended use.

If any material point is unclear, the integration should remain experimental, opt-in, or disabled by default.

## Current research targets

The initial research scope includes Claude Code, OpenCode, OpenAI Codex, Google Antigravity, and other MCP-capable or CLI-based coding agents.

Their names appearing in this repository do not mean the project claims stable compatibility.

Provider terms and automation surfaces change. Each adapter must be validated against current documentation when implemented and maintained.

## Account-safety goal

No local tool can guarantee that a provider will never suspend or restrict an account. Enforcement systems and contract interpretation are controlled by the provider.

Cliostra's goal is narrower and realistic:

> stay on documented interfaces, preserve provider controls, avoid credential abuse, avoid quota evasion, and clearly disable integrations whose policy status is materially uncertain.

That principle should be treated as part of the architecture, not as an optional disclaimer added after implementation.
